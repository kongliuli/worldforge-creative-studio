# 13 — 演进计划（v3+ 指导性路线图）

> **性质**：指导性文档，只规划、不排期到日历时间。依据 2026-07-14 对 `src/` 与 `tests/` 的全量代码梳理。
> **前置**：[12-实现状态总表](./12-实现状态总表.md)（v1、v2 已全部完成）；产品边界见 [10-MVP边界与迭代](./10-MVP边界与迭代.md) 与 [reference/09](./reference/09-MVP范围与路线图.md)。

## 一、现状结论（2026-07-14 梳理）

### 1.1 已站稳的部分

| 层 | 状态 |
|----|------|
| 架构分层 | Core（租户引擎 + 能力接口）/ Infrastructure（编排 + EF）/ AI（插件）/ Server（Minimal API）边界清晰，扩展新租户无需改编排 |
| 核心功能 | 手稿树（含拖拽 reorder）、TipTap + @Entity mention、实体 CRUD、矛盾检测双轨（规则 + Ollama LLM）、AutoDetectOnSave、按项目分库、ZIP 导入 |
| 前端 | Vue3 + Pinia + Vite，三栏工作区、租户 skinId 换肤、PWA-1（离线项目列表只读） |
| 测试 | Core 9 例 + AI 5 例 + Playwright smoke 1 例，CI 已接 GitHub Actions |

### 1.2 与「离线优先创作工坊」愿景的核心差距

按影响排序：

1. **数据真相仍在服务端**：SQLite 挂在 Server 进程里，离线只能读缓存列表、不能写作。「客户端权威」目前只是文档口径（09 §一）。
2. **商业化闭环缺失**：license/verify 是长度 ≥8 即通过的桩；无导出（Markdown/EPUB/PDF）、无安装分发形态，用户无法「买断 + 带走数据」。
3. **测试断层**：Infrastructure 六个服务与全部 API 端点零测试，恰好是业务逻辑最集中的一层。
4. **AI 层只到「能跑」**：Embedding 列有 schema 无生成/检索；确定性规则仅 1 条；检测每次追加新记录不去重；detect API 不传 focusDocumentId；Ollama 流式接口返回空。
5. **占位资产**：Legacy/Health 租户注册了 PluginId 但无实现类；`EntityRelationship`/`EntityTag` 有表无 API；`EntityPanel` 只支持角色。

### 1.3 已知技术债（小、应尽早还）

| 项 | 位置 | 处理 |
|----|------|------|
| 注册库 `EnsureCreated` vs 项目库 `MigrateAsync` 策略不一致 | `Infrastructure/DependencyInjection.cs` vs `ProjectDbContextFactory.cs` | 注册库也走 Migrations，否则未来加列即断 |
| 检测结果无去重/关闭旧 run | `ContradictionService.DetectAsync` | 同规则同实体对的 open 矛盾先关闭或合并 |
| `HelloWorld.vue` 脚手架残留 | `ClientApp/src/components/` | 删除 |
| `reference/14` 状态描述已过期 | `docs/design/reference/` | 标注「已被 12 取代」即可，不必维护 |
| 版本号 `0.1.0-skeleton` | `ApiEndpoints.cs` | 随 v3 发布改为语义化版本 |

## 二、演进阶段总览

原则：**先让已有功能可信（测试 + 债），再决定形态（离线/桌面），再收钱（license + 导出），AI 深化贯穿其后**。多租户（Legacy/Health）与多设备同步刻意押后 — 与 reference/12 红线一致。

```
v3 质量与补洞 ──► v4 客户端权威（离线写作）──► v5 商业化闭环 ──► v6 AI 深化 ──► Phase 2+ 同步/多租户
      │                    │
      └── 技术债清零        └── 形态决策：Electron vs PWA+IndexedDB（本阶段唯一重大决策）
```

## 三、v3 — 质量与补洞（下一个 /loop 清单）

目标：v1/v2 功能达到「可对外演示、改动不心虚」的状态。全部在现有架构内，无新依赖决策。

| 优先级 | 交付 | 内容 | 涉及 |
|:------:|------|------|------|
| 1 | Infrastructure + API 测试 | `WebApplicationFactory` + SQLite 内存库，覆盖 Project/Manuscript/Entity/Contradiction 服务与端点 happy path + 关键 guard（不存在的 id、跨项目访问） | 新增 `tests/WorldForge.Server.Tests` |
| 2 | 检测去重 | 重跑 detect 时按（RuleId/PluginId + 实体对）关闭旧 open 记录再写新；detect API 支持可选 `focusDocumentId` | `ContradictionService`、`ApiEndpoints` |
| 3 | 注册库 Migrations | 注册库从 `EnsureCreated` 切到 Migrations，补首个 migration | `RegistryDbContext` |
| 4 | 实体面板扩展 | `EntityPanel` 支持 Location/Faction/Item/TimelineEvent 的列表 + 创建 + 编辑（API 已就绪，纯前端） | `ClientApp` |
| 5 | TimelineEvent UI | 时间线视图（立项 ⬜ 项，简单纵向列表即可，不做甘特图） | `ClientApp` |
| 6 | Markdown 导出 | `GET /api/projects/{id}/export/markdown`：手稿树 → ZIP（TipTap JSON → Markdown 已有 WordCounter 可参考遍历逻辑）。这是「数据可带走」的最低承诺，也是 v4 迁移工具的地基 | Server + Infrastructure |
| 7 | 小债清理 | 删 `HelloWorld.vue`；版本号改 `0.3.0`；`reference/14` 顶部加过期标注 | 杂项 |

**验收**：`dotnet test` 用例数从 14 → ≥ 40；重复 detect 不再累积重复矛盾；能导出 Markdown ZIP 并 re-import 回环。

## 四、v4 — 客户端权威与离线写作（PWA-2）

目标：兑现「离线优先」承诺。**本阶段必须先做一次形态决策**，其余工作依赖该决策。

### 4.1 形态决策（唯一重大分叉）

| 方案 | 路径 | 优 | 劣 |
|------|------|----|----|
| A：Electron 壳 | Server 以本地进程随壳启动，SQLite 天然本地 | 改动最小（复用全部现有代码）、原生 SQLite、Scrivener 目录导入可行 | 包体大、需签名分发 |
| B：纯 PWA + IndexedDB 队列 | 前端本地库 + SyncQueue 重放 | 无安装包、Web 分发 | 等于重写数据层，双真相源冲突处理复杂 |

**建议：方案 A**。现有后端资产全部保留，「客户端权威」由部署形态实现而非代码重写；与 09 §6.6「Electron 与 PWA 共享 ClientApp 构建产物」预案一致。方案 B 仅当 A 的分发成本被验证不可接受时再启动。

### 4.2 工作项（按方案 A）

| 优先级 | 交付 |
|:------:|------|
| 1 | Electron 壳工程：启动时拉起 Kestrel 本地进程（随机端口），加载 ClientApp `dist/` |
| 2 | 数据目录迁移到用户目录（`%APPDATA%/WorldForge` 等），保留 `Data/` 开发模式 |
| 3 | 打包流水线：electron-builder + CI 产物（win-x64 优先） |
| 4 | Scrivener 目录（非 ZIP）导入，利用 Electron 文件系统权限 |
| 5 | PWA 路线保留为 Web 试用版：只读 demo，不再追 PWA-2 |

**验收**：断网状态下完成「创建项目 → 写作 → 检测 → 导出」全流程。

## 五、v5 — 商业化闭环

目标：可以真实收款交付。依赖 v4 的分发形态。

| 优先级 | 交付 |
|:------:|------|
| 1 | Gumroad license 校验替换桩：离线签名校验（Ed25519 公钥内置，license 文件含签名），避免强制联网激活 |
| 2 | EPUB 导出（在 v3 Markdown 导出管线上加一个 renderer；QuestPDF/PDF 可押后） |
| 3 | 试用限制策略（如项目数/字数上限），license 解锁 |
| 4 | 自动更新通道（electron-updater 或手动检查） |

**验收**：无 license 时功能受限、合法 license 离线可激活、导出 EPUB 可在主流阅读器打开。

## 六、v6 — AI 深化

目标：把「本地 AI 矛盾检测」从 demo 级拉到卖点级。与 v5 可部分并行。

| 优先级 | 交付 |
|:------:|------|
| 1 | 确定性规则扩容：关系对称性（A 是 B 之父 ↔ B 是 A 之子）、死亡后出场、地点归属冲突 — 每条规则一个类 + 单测，零 LLM 成本 |
| 2 | Embedding 落地：Ollama embeddings API 生成 `Note.Embedding`，语义检索「相关段落」喂给 LLM 检测，替代现在的全量摘录 |
| 3 | Ollama 流式实现 + 检测进度 UI（`GetStreamingResponseAsync` 现返回空） |
| 4 | 模型管理：检测 Ollama 是否在线/模型是否已拉取，引导 UI；`PreferredOllamaModel` 已贯通，补模型列表接口 |
| 5 | 误报反馈闭环：矛盾「忽略」原因回填，用于 prompt 迭代 |

**验收**：规则数 ≥ 4；万字项目检测延迟与 token 成本相对全量摘录下降有实测数字。

## 七、Phase 2+（刻意押后，不进 /loop）

以下明确 **不做**，触发条件写明：

| 项 | 触发条件 |
|----|---------|
| PostgreSQL + SyncQueue 多设备同步 | 付费用户明确要求多设备且 ≥ 一定比例（见 reference/09 指标） |
| Yjs CRDT 协作 | 同步上线且出现协作需求；**不与 SyncQueue 混用**（reference/12 红线） |
| Legacy/Health 租户激活 | Creative 租户商业验证通过后，作为第二增长曲线立项 |
| `EntityRelationship`/`EntityTag` API | v6 关系规则需要时一并落地，不提前建空 API |
| 整章 AI 代写 | 不做（产品红线） |
